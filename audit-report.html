Orbis — personal intelligence system — Audit Report

2026-09-28 &middot; Next.js 16.3 (App Router, Turbopack) · React 19 · TypeScript (strict) · Supabase (Postgres + RLS + Storage + Auth) · Vercel &middot; Whole repository at main (cb1567a) plus another session's uncommitted work in the tree; production reached only for public GETs (login, manifest, robots, well-known files). One production build measured. No Lighthouse, no e2e run, no access to the Supabase or Vercel dashboards.

52 F

Overall health

Orbis is carefully built underneath: row-level security on every table, encrypted connection tokens, a privacy-aware AI router, strict TypeScript and friendly error handling. What stands between it and a product strangers pay for is mostly around it, not in it. Right now anyone can sign up on the live site, there is no privacy policy or account deletion (both app stores require them), Gmail and the broker connections need approvals or commercial terms before strangers can use them, and the app renders its whole home page two or three times on every open. The quickest wins (closing sign-up, security headers, stopping the double renders, code-splitting the tabs) are a day or two; store launch and billing are weeks.

HIGH Anyone can create an account on the live site Security
lib/security/access.ts; production /login serves signupOpen:true

ORBIS_ALLOWED_EMAILS is not set in Vercel, so the Create account button is live. A stranger can store financial and health data in an app with no privacy policy, no terms, no way to delete their account and no upload rate limits (see the medium findings), and every stranger shares your free AI and data-provider quotas.

Fix

Set ORBIS_ALLOWED_EMAILS=<your address> in Vercel → Project → Settings → Environment Variables (Production), then redeploy. Open sign-up again deliberately once privacy, terms, deletion and rate limits exist.
You must do this yourself: Set the env var in the Vercel dashboard today. Also check Supabase → Authentication → Users for accounts you do not recognise.
HIGH Home renders the whole page twice on every open Performance
components/orbis-app.tsx:515

The Home effect calls router.refresh() on mount and on every return from background, so each open re-runs the ~34-request server render a second time. On 4G that is a visible re-render and double the database load.

Fix

Skip the refresh on first mount (ref flag) and only refresh on visibility after the app was hidden for 60 s or more. Better: refresh only the slices that change instead of router.refresh().
HIGH Every save renders the full page twice (revalidatePath plus router.refresh) Performance
app/finance/actions.ts:23 and 53 other revalidatePath('/') calls; 33 router.refresh() call sites e.g. components/orbis-app.tsx:201

A server action that revalidates already returns a fresh page; the client then asks for another one. Saving a journal entry or confirming a transaction costs about 68 database round-trips and two full payloads before the screen settles.

Fix

Keep revalidatePath in the actions and delete the router.refresh() calls that follow them. Longer term, tag per-slice caches ('use cache' + cacheTag) so a journal save does not re-query finance, brokers and health.
HIGH Background Home requests make the user's own taps wait Performance
components/orbis-app.tsx:95 (loadBriefPortfolioAction, loadHomeBriefAction)

Next runs server actions one at a time per client. The portfolio fetch and the AI brief (up to 20 s per model) are queued on every Home mount, so tapping Done on a routine, Sync or Save can sit dead for seconds.

Fix

Move these reads to GET route handlers called with fetch, or render them server-side inside <Suspense>. Keep server actions for writes.
HIGH The AI home brief is generated 2–3 times per open and burns the daily quota Performance
components/orbis-app.tsx:123; lib/home/ai-brief.ts:113

The request fires with weather=null, again when weather arrives and again when the portfolio lands; each misses the saved brief. The 12-a-day limit is gone after about five opens, and the written brief appears late.

Fix

Wait until weather has settled (ready, error or needs city) and the portfolio has loaded or timed out before asking; debounce data changes.

MEDIUM No security headers (CSP, frame blocking, HSTS, nosniff, referrer, permissions) Security
next.config.ts:3-10

The screen with the PIN pad and broker-key form can be framed by any site (clickjacking), and there is no second line of defence if an XSS ever lands. X-Powered-By: Next.js is sent.

Fix

MEDIUM Password can be changed without re-authentication, even while the app is locked Security
app/auth/actions.ts:132-146; app/reset-password/page.tsx:11-14

Anyone with a signed-in browser (a locked phone left open, or a stolen session cookie) can set a new password and take over the account. The PIN/passkey lock guards the app's server actions but not the data API.

Fix

Allow updatePassword only with a fresh recovery/OTP sign-in, or with the current password plus an unlocked app. Describe the lock honestly in the UI or move it into RLS with a short-lived 'unlocked' claim.
You must do this yourself: Supabase → Auth: enable 'Secure password change' and 'Leaked password protection'.
MEDIUM Push endpoints can point anywhere (blind SSRF and fan-out from the cron) Security
supabase/migrations/202609240015_profile_journal_notifications.sql:64-82; lib/notifications/push.ts:39-45

RLS lets users insert push_subscriptions directly, bypassing the https check and 10-device cap. The dispatcher then POSTs to every stored URL every 5 minutes with no timeout, so one account can make Orbis hit arbitrary hosts and delay everyone's notifications. notification_log rows can also be edited to dodge the test-send limit.

Fix

Add a CHECK limiting endpoint hosts to the real push services, revoke direct INSERT/UPDATE (write through the server action only), pass { timeout: 5000 } to web-push and limit concurrency; revoke update on notification_log and grant update (read_at) only.
MEDIUM No rate limits or storage quotas on uploads, parsing and sync Security

Fix

Add a per-user token bucket (Postgres RPC like the existing consume_* functions, or Upstash) on uploads, parse and sync; cap documents and total bytes per user; issue signed upload URLs instead of open bucket INSERT.
